# Daily Stats — Telegram-дневник

Персональный дневник привычек и самочувствия в одном Telegram-боте: сигареты, валять дурака, снюс (срок шайбы), сон, настроение, самочувствие, кофеин, алкоголь, активность, заметки и кастомные метрики. Статистика и графики строятся за выбранный период. Оплата — внутренний баланс, который владелец пополняет вручную.

В сервисе **ровно один Telegram-бот**. Админ-панель владельца находится в нём же, отдельного админ-бота нет.

## Возможности

### Для пользователя

- Быстрая запись «сейчас» или указание даты и времени вручную
- Сигареты; валять дурака; снюс (купил шайбу / закончилась, сколько хватило); сон (отход / пробуждение / качество); настроение, самочувствие
- Кофеин и алкоголь с объёмом (мл / 0.5л), физическая активность с длительностью (35 мин / 1ч 20м), текстовые заметки
- Кастомные метрики: шаблоны или свой тип (число, текст, да/нет, выбор, время, длительность)
- История за день, вчера, дату или диапазон; правка и удаление записей
- Конструктор статистики: период → показатели → текст или график
- Сравнение показателей (корреляция Пирсона со явной оговоркой, что это не причинность)
- Напоминание оценить день; ручной сценарий «Оценить день»
- Свой часовой пояс; все границы дня считаются в нём
- При нулевом балансе история, статистика, графики и настройки остаются доступны; новые и изменённые записи — нет

### Для владельца

- Админ-панель в том же боте (кнопка только у `OWNER_TELEGRAM_ID`)
- Поиск пользователей, карточка, статистика пользователя
- Пополнение / списание / установка баланса, индивидуальная цена ₽/день
- Журнал финансовых операций, статистика сервиса
- Блокировка и разблокировка пользователей
- Алерты о критических ошибках в этот же чат
- Восстановление из архива, который бот шлёт в Telegram: кнопка в админке или `./restore.sh`

## Архитектура

Один Python-процесс, один event loop, **один экземпляр `Bot()`** (создаётся в `bot.py`). Запуск через long polling aiogram 3.x.

```text
Telegram  →  aiogram Dispatcher  →  handlers  →  services  →  SQLite (aiosqlite, WAL)
                                      ↑
                               APScheduler (списания, напоминания, backup, бэкап в Telegram)
```

- Слой БД: `database/` — подключение, WAL, миграции, backup/restore, параметризованные запросы
- Бизнес-логика: `services/` — баланс, биллинг, статистика, графики, напоминания
- Telegram: `handlers/` + `keyboards/` + `states/`
- Пользователи изолированы: все выборки и изменения идут с `telegram_id` текущего пользователя
- Права админа проверяются **в каждом** административном handler, не только скрытием кнопки

Целевое окружение: VPS, 1 CPU, 2 ГБ RAM, Docker.

## Быстрый запуск

На машине с Docker, systemd и mihomo достаточно применить конфиги из репозитория:

```bash
cp .env.example .env
# Заполните BOT_TOKEN, OWNER_TELEGRAM_ID, OWNER_CONTACT

chmod +x deploy.sh
./deploy.sh
docker compose logs -f bot
```

`./deploy.sh` ставит mihomo (`11808` / `19090`), systemd-юниты, `docker-compose.override.yml` и поднимает контейнер. Пакет: `yay -S mihomo`. Нужен sudo.

Вручную, без скрипта:

```bash
mkdir -p data backups
# Если контейнер не может писать в volume:
# sudo chown -R 1000:1000 data backups

docker compose build
docker compose up -d
docker compose logs -f bot
```

В логах ожидаются `SQLite WAL mode confirmed` и `Polling started`.

Откройте бота в Telegram → `/start` → выберите часовой пояс.

По умолчанию `DEFAULT_DAILY_PRICE=10`. Новый пользователь с балансом 0 не сможет создавать записи, пока владелец не пополнит баланс. Для бесплатного теста поставьте `DEFAULT_DAILY_PRICE=0`.

Остановка:

```bash
docker compose stop bot    # SIGTERM → shutdown-backup, затем выход
docker compose down        # контейнер останавливается, volumes на хосте остаются
```

Не запускайте два контейнера на одном файле SQLite.

## Прокси (блокировки Telegram)

Если Telegram недоступен с сервера, бот ходит через **отдельный** mihomo на хосте, а не через личный v2rayN.

Порты специально разведены, чтобы оба клиента могли работать одновременно:

| Клиент | Назначение | Порты |
|---|---|---|
| v2rayN | ваш трафик | SOCKS/HTTP `10808` / `10809` |
| mihomo | только бот | mixed `11808`, API `19090` |

1. Порты берутся из `deploy/mihomo/config.yaml`, а не с `10808` v2rayN.
2. Примените всё сразу:

```bash
./deploy.sh
```

Только override (без systemd/mihomo):

```bash
chmod +x generate-docker-override.sh
./generate-docker-override.sh
docker compose up -d --build
```

Получится примерно:

```yaml
services:
  bot:
    network_mode: host
    environment:
      HTTP_PROXY: http://127.0.0.1:11808
      HTTPS_PROXY: http://127.0.0.1:11808
      NO_PROXY: localhost,127.0.0.1
      ALL_PROXY: socks5://127.0.0.1:11808
      TELEGRAM_PROXY_URL: socks5://127.0.0.1:11808
```

`network_mode: host` нужен, чтобы `127.0.0.1:11808` внутри контейнера был тем же портом, что слушает mihomo на машине. Файл override не коммитится.

Проверка:

```bash
curl -s --max-time 5 -x "socks5://127.0.0.1:11808" https://api.telegram.org
docker compose logs -f | grep telegram_proxy
```

В логах должно быть `telegram_proxy_enabled`. Aiogram ходит через `AiohttpSession(proxy=...)` (пакет `aiohttp-socks`).

Где Telegram доступен напрямую, оставьте `TELEGRAM_PROXY_URL` пустым и **не** запускайте `generate-docker-override.sh`.

## Переменные окружения

Файл `.env` не коммитится. Шаблон — `.env.example`.

| Переменная | Обязательно | По умолчанию | Назначение |
|---|---|---|---|
| `BOT_TOKEN` | да | — | Токен единственного бота |
| `OWNER_TELEGRAM_ID` | да | — | ID владельца: админка и алерты |
| `OWNER_CONTACT` | нет | «владелец сервиса» | Контакт в настройках пользователя |
| `DEFAULT_TIMEZONE` | нет | `Europe/Moscow` | Пояс при регистрации, пока пользователь не выбрал свой |
| `DEFAULT_DAILY_PRICE` | нет | `10` | Цена ₽/день для новых пользователей |
| `DEFAULT_SLEEP_TIME` | нет | `23:00` | Запасное время сна в настройках |
| `REMINDER_HOURS_BEFORE_SLEEP` | нет | `3` | За сколько часов до среднего отхода ко сну слать напоминание |
| `REMINDER_FALLBACK_TIME` | нет | `20:45` | Время напоминания, если нет 3 ночей сна |
| `DB_PATH` | нет | `/app/data/database.sqlite3` | Путь к БД **внутри контейнера** |
| `BACKUP_PATH` | нет | `/app/backups` | Каталог backup внутри контейнера |
| `BACKUP_INTERVAL_HOURS` | нет | `6` | Период автоматического backup на диск |
| `BACKUP_KEEP` | нет | `14` | Сколько копий на диске хранить |
| `TELEGRAM_BACKUP_INTERVAL_MINUTES` | нет | `30` | Минимум минут между беззвучными архивами в группу бэкапов (0 — выкл). Отсчёт от последней успешной отправки. Старое имя `TELEGRAM_BACKUP_INTERVAL_HOURS` ещё читается |
| `TELEGRAM_BACKUP_ROOT` | нет | корень приложения | Откуда брать `.env` и конфиги для архива. В Docker — `/host` |
| `BILLING_CHECK_MINUTES` | нет | `15` | Интервал проверки ежедневных списаний |
| `REMINDER_CHECK_MINUTES` | нет | `1` | Интервал проверки напоминаний |
| `LOG_LEVEL` | нет | `INFO` | Уровень JSON-логов |
| `TELEGRAM_PROXY_URL` | нет | пусто | SOCKS5 для Telegram API, например `socks5://127.0.0.1:11808` (mihomo). Пусто, если Telegram доступен напрямую |

Секреты в исходный код не зашиваются. В логи не пишутся токен и похожие строки.

На хосте БД и backup монтируются так:

```text
./data     →  /app/data
./backups  →  /app/backups
.          →  /host (только чтение: .env и конфиги для бэкапа в Telegram)
```

## База данных и миграции

SQLite + aiosqlite, режим **WAL**, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`.

Все SQL-запросы параметризованы. Пользовательские данные не конкатенируются в текст запроса.

Версия схемы хранится в `PRAGMA user_version`. Требуемая версия приложения — константа `REQUIRED_DB_VERSION` в `config.py` (сейчас `4`).

При старте:

1. Подключение и проверка WAL
2. `PRAGMA integrity_check`; при повреждении — карантин файла и попытка restore
3. Сравнение `user_version` с `REQUIRED_DB_VERSION`
4. Если версия ниже — backup `pre_migrate`, затем SQL из `migrations/` по возрастанию номера
5. Установка `user_version`
6. Запуск бота

Файлы миграций: `migrations/001_initial.sql`, далее `002_....sql` и т.д. Префикс имени — целое число версии.

Чтобы выпустить схему новой версии:

1. Добавить `migrations/00N_описание.sql`
2. Выставить `REQUIRED_DB_VERSION = N` в `config.py`
3. Собрать и выкатить образ; миграция применится сама

Если файл БД новее кода (`user_version` > требуемой), процесс завершится с ошибкой — сначала обновите приложение.

## Резервные копии

Backup идёт через SQLite Online Backup API: в копию попадают и страницы из WAL, последние записи не теряются.

Когда создаётся копия на диск:

- по расписанию (`BACKUP_INTERVAL_HOURS`)
- перед миграциями (`pre_migrate_...`)
- при graceful shutdown (`SIGTERM` / `docker compose stop`) — `shutdown_...`
- при ошибке старта, если возможно — `crash_...`

Имена: `{prefix}_YYYYMMDD_HHMMSS.sqlite3` в `./backups`. Хранятся `BACKUP_KEEP` последних файлов, остальные удаляются.

Отдельно в привязанную группу уходит архив `.tgz` (gzip-tar, сжатие **pigz**; расширение одно, чтобы Telegram/Ark не принимали файл за «просто .gz»): снимок БД + `.env` + конфиги (`docker-compose.yml`, `docker-compose.override.yml`, `Dockerfile`, `config.py`, `deploy/` и т.п.). Имя файла: `daily-stats-backup_01-08-2026_10-10-10_{short-hash}_{тема-коммита}_db{версия}.tgz` (дата и время в поясе владельца). Коммит — тот, что был **собран в образ** (`docker compose build` / `./deploy.sh` передают `GIT_COMMIT` и `GIT_COMMIT_TITLE`). Сообщение **без звука** (`disable_notification`). Интервал — `TELEGRAM_BACKUP_INTERVAL_MINUTES`, по умолчанию **30 минут**. Отсчёт идёт от последней **успешной** отправки (время пишется в `system_info`). Если с тех пор прошло больше интервала — в том числе после рестарта — архив уходит сразу, и таймер стартует заново. `0` выключает автоотправку. Пока группа не привязана, задание пропускается. Владелец добавляет бота в группу (или пишет там `/backup_here`) — архивы начинают уходить туда. В личку владельцу архив приходит только по кнопке **📤 Сделать бэкап сейчас**. Если файл `.env` в контейнере не читается (права 600), entrypoint копирует его в `/app/.env.runtime` для архива. Если и это недоступно — в архив попадает снимок переменных из окружения.

Docker-логи ограничены: `max-size: 10m`, `max-file: 5`.

## Обновление

`./deploy.sh` ставит systemd-таймер `daily-stats-update.timer`. Дальше пуш в `main` не выкатывается сам: хост забирает `origin/main` и пишет владельцу в этот же бот кнопками **Обновить** / **Позже**. После подтверждения собирает образ, ждёт, пока бот не будет простаивать (нет записей в базу, бэкапа, списаний и обработки нажатий), и только потом переключает контейнер. **Позже** пропускает этот коммит и спросит снова, когда в `main` появится другой. Тот же бот пишет владельцу **перед** выкаткой, **после** успешного запуска и **если** сборка, простой или старт сломались.

Первый раз (или после смены юнитов) на сервере как обычно:

```bash
git pull --ff-only
./deploy.sh
```

Потом достаточно пуша в `main` и подтверждения в боте. Вручную то же самое:

```bash
./deploy/update.sh          # нет изменений — тихо; есть — спрашивает в боте
./deploy/update.sh --force  # выкатить без подтверждения
```

Откат:

```bash
docker compose stop bot
# вернуть предыдущий образ/тег
# при необходимости восстановить БД из backups (см. ниже)
docker compose up -d
```

Не используйте `docker compose down -v` — это не нужно для обновления и опасно, если volumes именованные. Сейчас данные на bind-mount `./data` и `./backups`, они переживают `down`.

## Восстановление БД

### Автоматически

Если основная БД не проходит `integrity_check`:

1. Повреждённый файл **не удаляется** — копируется как `database.sqlite3.damaged.TIMESTAMP` (вместе с `-wal`/`-shm`, если есть)
2. Берётся самый новый `*.sqlite3` из `backups/`
3. Восстановленная БД снова проверяется
4. Только после успешной проверки стартует polling

Если backup нет — процесс завершается, Docker перезапускает контейнер (`restart: unless-stopped`). Владельцу уходит алерт, если токен ещё позволяет отправить сообщение.

### Вручную

```bash
docker compose stop bot

cp data/database.sqlite3 "data/database.sqlite3.damaged.$(date +%Y%m%d_%H%M%S)"
# при наличии:
# cp data/database.sqlite3-wal "data/database.sqlite3.damaged.$(date +%Y%m%d_%H%M%S)-wal"

cp backups/backup_YYYYMMDD_HHMMSS.sqlite3 data/database.sqlite3
rm -f data/database.sqlite3-wal data/database.sqlite3-shm

docker compose up -d
docker compose logs -f bot
```

Подставьте реальное имя файла из `ls -lt backups/`.

## Восстановление из бэкапа Telegram

Архив `daily-stats-backup_….tgz` содержит снимок БД, `.env` и копии конфигов. Им можно поднять бота на новом сервере или откатить повреждённую базу. Старые файлы `.tar.gz` тоже подходят.

### Скрипт на сервере

На хосте достаточно `tar`/`gzip`, Python не нужен. Если контейнер запущен, скрипт его остановит.

```bash
chmod +x restore.sh
./restore.sh ~/Downloads/daily-stats-backup_01-08-2026_10-10-10_….tgz
```

Что произойдёт:

- текущая `data/database.sqlite3` уйдёт в `data/database.sqlite3.pre_restore.TIMESTAMP`
- на её место встанет база из архива
- `.env` из архива запишется в корень (старый файл — `.env.pre_restore.TIMESTAMP`); `--keep-env` оставляет текущий
- конфиги из архива копируются в `restored-configs/` **только для просмотра**, сами `docker-compose.yml` / `config.py` не перезаписываются

Новый сервер:

```bash
git clone <repo> daily-stats
cd daily-stats
./restore.sh ~/Downloads/daily-stats-backup_….tgz
./deploy.sh
```

Если Telegram с этой машины доступен напрямую, без mihomo:

```bash
./restore.sh ~/Downloads/daily-stats-backup_….tgz --start
```

`--start` делает `docker compose up -d --build`.

Внутри контейнера то же самое: `python -m services.telegram_restore /path/to/backup.tgz` (сразу ставит БД) или `--stage` (кладёт `backups/pending-restore.tar.gz`, бот применит файл при старте).

### Кнопка в админке

Раздел **📦 Бэкапы** в админ-панели:

- **📤 Сделать бэкап сейчас** — сразу собирает тот же архив (БД + `.env` + конфиги) и присылает его **в этот чат** (личку). Автоматические архивы уходят в привязанную группу каждые 30 минут. Следующий автоматический бэкап отсчитывается заново.
- **🔄 Восстановить из файла** — пришлите `daily-stats-backup_….tgz`, подтвердите, бот перезапустится с этими данными.
- **🗄 Копии на диске** — снимки SQLite из `backups/` (без `.env`): отправить файл в чат или восстановить и перезапустить.

Бот уже должен отвечать (хотя бы пустая/новая база). Восстановление из архива Telegram:

1. Админ-панель → **📦 Бэкапы** → **🔄 Восстановить из файла**
2. Перешлите сообщение с архивом или отправьте файл `daily-stats-backup_….tgz`
3. Проверьте превью (версия БД, целостность, число пользователей)
4. **🔄 Восстановить и перезапустить**

Бот сохранит текущую базу, положит архив в `backups/pending-restore.tar.gz` и выйдет с кодом 0. Docker (`restart: unless-stopped`) поднимет процесс заново; при старте архив применяется, затем приходит подтверждение в этот же чат.

Telegram отдаёт боту файлы **не больше 20 МБ**. Если архив крупнее — используйте `./restore.sh` на сервере.

Нельзя накатить бэкап, у которого `user_version` **новее** текущего приложения: сначала обновите код. Более старая схема допустима — миграции накатятся сами.

## Инструкция владельца

Кнопка **🛠 Админ-панель** появляется в главном меню, только если ваш Telegram ID совпадает с `OWNER_TELEGRAM_ID`.

| Действие | Где |

## Баланс и списания

Модель: индивидуальная цена ₽/сутки в поле `users.daily_price`.

Каждый локальный день пользователя система пытается списать эту сумму. Ключ идемпотентности: `daily:{telegram_id}:{YYYY-MM-DD}` — одно списание на день, в том числе после простоя и перезапуска.

- Хватает денег → списание, `paid_until_date` = этот день, записи можно создавать
- Не хватает → остаток (если был) списывается, день не считается оплаченным, новые записи недоступны
- Цена `0` → день бесплатный, запись разрешена
- Если день уже оплачен, писать можно даже при балансе `0` до следующей полуночи в поясе пользователя

После простоя сервис догоняет пропущенные дни с даты последнего списания (или с даты регистрации) по «сегодня» в поясе пользователя, без двойного списания.

История и статистика при недостатке средств **работают**. Нельзя обойти запрет, отредактировав старую запись: правка и удаление тоже требуют права на запись.

## Напоминания

Напоминание «оценить день» (настроение и самочувствие):

- считается среднее время отхода ко сну за **последние 3 завершённые** ночи (круговое среднее, корректно вокруг полуночи);
- сообщение уходит за `REMINDER_HOURS_BEFORE_SLEEP` часов до этого времени;
- если ночей меньше трёх — используется `REMINDER_FALLBACK_TIME`;
- если за сегодня оценки уже есть, повторно не шлётся;
- расписание хранится в таблице `reminders` и восстанавливается после рестарта без дублей;
- после изменения записей сна время следующего напоминания пересчитывается.

Вручную то же самое: **🌙 Оценить день**.

handlers/              Telegram-сценарии (FSM, inline-кнопки)
services/              биллинг, статистика, графики, напоминания, записи, telegram backup/restore
database/              WAL, миграции, backup, параметризованный Repo

## Логи и надёжность

- Логи в **JSON** в stdout (их забирает Docker)
- Пишется: старт/стоп, ошибки, миграции, backup, restore, админские и денежные операции
- Не пишется: токен, пароли, секреты
- Ошибка в одном handler не роняет процесс: middleware логирует, отвечает пользователю без traceback, владельцу уходит алерт
- Критическая ошибка старта (невосстановимая БД) завершает процесс с кодом 1 — Docker перезапускает контейнер
- `restart: unless-stopped`, `stop_grace_period: 30s`

Алерт владельцу (этот же бот): тип, время UTC, описание, контекст, traceback при необходимости. Пользователю внутренний traceback не показывается.
